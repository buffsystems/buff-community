## Что нужно

| | Требование |
|---|---|
| Linux | **Ubuntu 22.04 или 24.04**, amd64, ядро не ниже 5.7, пользователь с `sudo`, установленный `git`. Раннеры работают в [Sysbox](https://github.com/nestybox/sysbox) — без привилегированных контейнеров и без сокета хоста |
| macOS, Windows | [Docker Desktop](https://docs.docker.com/desktop/); на Windows скрипт запускается из Git Bash. Sysbox здесь нет, поэтому **контейнер Buff работает привилегированным** — для личной машины, не для сервера |
| Ресурсы | минимум 4 CPU и 8 ГБ памяти (одна разработка за раз); рекомендуется 8 CPU и 16 ГБ для трёх одновременных — каждая разработка занимает до 1,5 ГБ. На диске около 12 ГБ под образы (стоковые, наш и собранная на месте песочница) плюс место под ваши репозитории: данные лежат в томах Docker, не в образе |
| Доступ | исходящий интернет: образы с ghcr.io и Docker Hub, суточная проверка лицензии на buff.systems, ваш эндпоинт модели |
| Модель | ключ к OpenAI-совместимому эндпоинту: [OpenRouter](https://openrouter.ai), свой LiteLLM, vLLM, Ollama и т. п. |

> На Linux убедитесь, что весь диск отдан корневому разделу или смонтирован под `/var/lib/docker` — образ сервера с корнем в 8 ГБ не подойдёт. На Apple Silicon образ (amd64) идёт через эмуляцию и работает заметно медленнее.

## Установка одной командой

Запускайте обычным пользователем с `sudo` — root не нужен:

```sh
git clone https://github.com/buffsystems/buff-community.git
cd buff-community
./install.sh
```

Скрипт задаёт пять вопросов (Enter — оставить значение по умолчанию, всё можно поправить потом в `.env`):

```
настройки установки (Enter — оставить как есть, поправить можно потом в .env)
имя вашей организации латиницей [company]: acme
почта администратора [admin@37.18.90.39]: you@example.com
адрес OpenAI-совместимого эндпоинта модели [https://openrouter.ai/api/v1]:
ключ эндпоинта (ввод скрыт):
модель, например openai/gpt-4.1 []: openai/gpt-4.1
пароли записаны в …/buff-community/.env (пароль администратора — ADMIN_PASSWORD)
```

Те же значения можно передать переменными окружения без диалога: `ORG=acme LLM_API_KEY=… ./install.sh`.

Дальше скрипт сам:

1. определяет режим — Linux (ставит Docker и Sysbox) или Docker Desktop (добавляет `docker-compose.desktop.yml`);
2. создаёт `.env` из `.env.example` со случайными паролями;
3. скачивает образ издания `ghcr.io/buffsystems/buff-community` и проверяет его;
4. собирает образ песочницы агента `buff-community-sandbox` поверх стокового Windmill и передаёт его во внутренний docker;
5. поднимает `docker compose` и показывает ход первого старта прямо в терминале — строки `[bootstrap]` до **готово** (несколько минут: базы, учётные записи, выкладка пайплайна).

Повторный запуск `./install.sh` на работающей установке безопасен: он только обновляет то, что изменилось.

## Настройки в `.env`

Файл `.env` лежит рядом с `docker-compose.yml`, права `600`. Что в нём стоит проверить:

| Переменная | Что это |
|---|---|
| `ORG` | имя вашей организации латиницей, например `acme` |
| `ADMIN_USER`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` | первый пользователь приложения, он же администратор; пароль сгенерирован, его можно заменить |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | эндпоинт, ключ и модель, например `https://openrouter.ai/api/v1`, `sk-or-…`, `openai/gpt-4.1` |
| `APP_URL` | адрес, по которому люди откроют приложение; по умолчанию — IP машины и порт 8138 |
| `APP_PORT`, `ADMIN_PORT`, `BIND_IP` | порты приложения (8138) и админки (8150), интерфейс, на котором они слушают |
| `RUNNERS` | сколько воркеров разработки запустить — столько разработок пойдут одновременно, по умолчанию 3. Выше предела лицензии значение не действует (Community — 15) |
| `BUFF_IMAGE`, `SANDBOX_IMAGE`, `WINDMILL_IMAGE` | версии образов; меняются при обновлении из `.env.example` |

Изменили `.env` — примените:

```sh
docker compose up -d
```

## Первый вход

**Приложение** — `APP_URL` (`http://<машина>:8138/app/`). Логин — `ADMIN_USER`, пароль — `ADMIN_PASSWORD` из `.env`.

![Вход в приложение](../assets/shots/ce-login.png)

После входа вы в своей организации, в её первом пространстве. Слева — разделы: «Спросить», «Глубокое исследование», «Коннекторы», «Сессии разработки», «База знаний». Задать первый вопрос можно сразу, как только появится лицензия (см. ниже).

![Пространство организации: «Спросить»](../assets/shots/ce-org.png)

**Админка** — `http://<машина>:8150`, пользователь `admin`, тот же пароль. Разделы: пользователи, проекты, репозитории, коннекторы, воркеры, пайплайн, конфигурация, использование, лицензия.

## Лицензия

Установка работает по лицензии Community: бессрочной, с [условиями](../LICENSE.md) внутреннего использования одной организацией. Пока лицензии нет, **новые задачи, прогоны, исследования и вопросы не стартуют**; вход и чтение работают.

1. В админке откройте «Лицензия», укажите название организации и почту администратора, поставьте галочку согласия на обработку этих данных и нажмите «Зарегистрировать».
2. Установка сама обращается к buff.systems и получает лицензию — обычно в течение минуты, не дольше часа. Статус сменится на «действует».

![Лицензия получена: пределы и дата последней проверки](../assets/shots/ce-admin-license.png)

Пределы — пользователей, одновременных разработок, организаций — подписаны в лицензии и показаны на той же странице; настройки установки выше них не действуют. Раз в сутки установка проверяет лицензию и передаёт четыре поля: идентификатор установки, версию, число пользователей и число раннеров. Отсутствие связи с buff.systems лицензию не прекращает. Для контура без интернета есть поле «Файл лицензии» — см. [Закрытый контур](#закрытый-контур).

## Пользователи

Самостоятельной регистрации нет: людей заводит администратор в админке → «Пользователи» → «Создать». Счётчик справа показывает, сколько мест лицензии занято. Учётные записи с пометкой «бот» — служебные агенты пайплайна (аналитик, разработчик, ревьюер), в лимит они не входят. Всем участникам видно всё в организации.

## Репозитории: центральный коннектор

В Community коннектор один и он встроен в установку: **«Центральный коннектор»** запускается внутри контейнера и сам сопрягается с вашей организацией при первом старте — в приложении в «Коннекторы» он появляется через минуту-две. Его настройки — файл `connector/connector.yaml` рядом с `docker-compose.yml`: там перечисляются git-провайдеры (GitLab, GitHub, Gitea, Bitbucket, в том числе self-hosted) и токены к ним; формат описан в комментариях самого файла. Токены остаются в этом файле на вашей машине.

Изменили файл — перезапустите коннектор:

```sh
docker compose exec buff supervisorctl restart services:connector
```

После этого подключите репозиторий в приложении: проект появится в разделе организации с его задачами, аудитами и настройками разработки.

![Проект с подключённым репозиторием: задачи и их этапы](../assets/shots/dev.png)

Коннектор видит сеть так же, как контейнер: до вашего git-сервера ему нужен сетевой доступ с этой машины.

## Первая работа: вопрос, исследование, задача

- **Спросить** — вопрос по документам и коду организации; ответ с источниками, только чтение. Самый быстрый способ проверить, что модель отвечает.
- **Глубокое исследование** — аналитик и ревьюер готовят документ (Markdown и PDF) по вашим источникам; занимает от десяти минут до часа в зависимости от модели.
- **Задача** — в проекте опишите задачу: аналитик уточнит её вопросами, после вашего «утвердить» разработчик реализует в песочнице, ревьюер проверит, на выходе — ветка и merge request в вашем репозитории.

## Docker Desktop (macOS, Windows)

На macOS и Windows `install.sh` сам переключается в режим Docker Desktop (на Linux его можно включить принудительно: `BUFF_MODE=desktop ./install.sh`). В этом режиме в `.env` раскрывается строка `COMPOSE_FILE=docker-compose.yml:docker-compose.desktop.yml`: Sysbox недоступен, и контейнер Buff запускается привилегированным с runtime `runc`. Это подходит для личной машины и не подходит для сервера. На Windows запускайте скрипт из Git Bash; Docker Desktop должен быть запущен заранее.

## Закрытый контур

Если машина не имеет выхода в интернет:

- положите файл образа издания и его `.sha256` в `images/` — `install.sh` загрузит его вместо скачивания; то же для песочницы: `images/buff-community-sandbox.tar.zst`;
- стоковые образы (PostgreSQL, Gitea, NATS, Windmill, Tika) перенесите своим реестром или `docker save`/`docker load`;
- лицензию получите на buff.systems для показанного в админке `instance_id` и вставьте в поле «Файл лицензии».

## Обновление

```sh
git pull
./install.sh
```

Впишите в `.env` новые `BUFF_IMAGE` и `SANDBOX_IMAGE` из обновлённого `.env.example` — скрипт скачает образ, пересоберёт песочницу и перезапустит контейнеры. Миграции базы применяются при старте. Версия установки видна в админке.

## Резервная копия

Все данные — в томах Docker: `pgdata` (базы), `gitea-data` (репозитории), `buff-data` (секреты, ключи, рабочие каталоги), `buff-docker` (слои внутреннего docker). Копия: остановите стек (`docker compose stop`), скопируйте тома любым привычным способом, запустите снова. Файл `.env` храните вместе с копией — в нём пароли.

## Диагностика

- `docker compose ps` — состояние контейнеров; `docker compose logs buff` — наш контейнер.
- `docker compose exec buff supervisorctl status` — сервисы внутри контейнера; `supervisorctl restart services:auth-worker` перезапускает один.
- Повторить первый старт безопасно: `docker compose exec buff buff-bootstrap` — все шаги идемпотентны.
- Раннеры не стартуют — проверьте, что образ песочниц есть во внутреннем docker: `docker compose exec buff /opt/docker-real/docker images`.
- Снести установку целиком: `docker compose down -v` (тома с данными удаляются) и `sudo rm -rf` каталога комплекта — `connector/state` пишет контейнер от root.
- Вопросы и ошибки — в [issues репозитория](https://github.com/buffsystems/buff-community/issues); как оформлять — в [CONTRIBUTING.md](../CONTRIBUTING.md). Техническая поддержка Community Edition не предоставляется.

## Что внутри

`docker compose` поднимает стоковые образы PostgreSQL, Gitea (внутреннее git-хранилище, пользователю не видно), NATS, Windmill (сервер и воркеры — число воркеров задаёт `RUNNERS`) и Apache Tika рядом с одним нашим образом `buff-community` (~1,4 ГБ), где под супервизором живут все сервисы Buff и внутренний docker. На Linux наш образ — системный контейнер Sysbox со своим docker внутри: в нём работают песочницы агентов, без `privileged` и без сокета хоста; в Docker Desktop тот же контейнер работает привилегированным. Воркеры Windmill запускают песочницы через сокет этого внутреннего docker на общем томе.

Песочница агента — отдельный образ `buff-community-sandbox`: `install.sh` собирает его на вашей машине поверх того же стокового образа Windmill (все рантаймы языков — паритет с SaaS), добавляя docker, движок Buff и MCP-серверы, и передаёт во внутренний docker без второго скачивания. Windmill загружается с ghcr.io на условиях его авторов и ни в один наш образ не входит; остальные сторонние компоненты — в [THIRD-PARTY.md](../THIRD-PARTY.md).
